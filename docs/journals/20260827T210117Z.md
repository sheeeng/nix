# Fix Stale GitHub Contributor Count After Force Push

After rewriting repository history to remove invalid contributors
(`claude-code[bot]` and `propose-pull-request[bot]`) and force-pushing,
the repository front page still showed 6 contributors. The contributors
page and the GitHub API (`/repos/{owner}/{repo}/contributors`) already
returned the correct 4, confirming the data was clean but the UI cache
was stale.

## Root Cause

GitHub caches contributor aggregations separately from the underlying
commit graph. A force push does not invalidate this cache. Background
jobs rebuild it lazily, and the refresh can take hours, days, or never
occur without a manual trigger.

## Workaround: Default Branch Rename Dance

Renaming the default branch and immediately renaming it back appeared
to trigger a contributor-index rebuild in this case. GitHub does not
document or guarantee this behavior. Use this approach only as a last
resort and review the following documented side effects first:

- Open pull requests whose head branch matches the renamed branch
  may close automatically.
- Workflow files and action references that hard-code the branch
  name will break until updated.

```shell
gh api --method POST repos/sheeeng/nix/branches/unstable/rename \
    --field new_name=unstable-tmp

gh api --method POST repos/sheeeng/nix/branches/unstable-tmp/rename \
    --field new_name=unstable
```

After the rename dance, hard-refresh the repository page
(⌘+Shift+R on macOS) to clear any browser-side cache.

Check for branch protection rules before renaming:

```shell
gh api repos/{owner}/{repo}/branches/{branch}/protection
```

If protection rules exist, verify that GitHub automatically
transferred them correctly after the rename.
